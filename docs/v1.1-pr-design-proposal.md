# LOADS v1.1 P1 design proposal — historical proposal

Approved with amendments: ASSISTED WEIGHT PR now compares the minimum assistance of any set with at least one actual rep, regardless of rep count. The same-rep proposal below is superseded. Classified publication is paused because v1 feed rendering cannot safely interpret the new load semantics. See `v1.1-p1-implementation.md` for the implemented contract and verification.

P0 is implemented separately. Nothing in this proposal authorizes or implements P1.

## Record versions and comparison history

- Add optional `prVersion: 1 | 2` to WorkoutSession. Missing means version 1. Stamp version 2 only on workouts started after the new rules ship; do not stamp historical records on read, copy, or repost.
- Add the same optional version to ActiveWorkout so a pre-update workout resumed after upgrade retains version 1. Missing active version also means version 1.
- A workout begun from a template is a new workout; the template must not determine its PR version.
- Version 1 evaluator preserves existing results, including first-record PRs, failed/stopped behavior, timestamp comparison, and the existing live-screen volume lookup behavior. Put the source context in the legacy adapter where necessary rather than silently harmonizing old differences.
- Version 2 evaluator filters completed sets with finite nonnegative weight and positive integer actual reps. Failed/stopped still count their actual positive reps. Invalid/blank values are not invented zeros; explicit zero is valid for BODYWEIGHT only as a weight input, and never as a rep count.
- For ordinary exercises, version 2 compares to valid sets from older records of either version: old data remains a usable baseline. Reposting a version 1 workout uses version 1.
- For PULL UP, compare only explicit matching load classifications. Missing classification remains legacy/unknown and is excluded from classified baselines. No inference from names, positive/zero weight, notes, or catalog equipment.
- Use strictly older finishedAt timestamps, excluding the current ID. Equal timestamps stay incomparable, matching existing behavior.
- Calculate version 2 volume per exercise block; compare all matching historical blocks, not only the first. Keep session-total volume as the sum of blocks. Do not merge duplicate blocks silently.

## FIRST RECORD

- One baseline per exercise name + load classification (not per PR/VOLUME focus or new weight). Valid older sets are required to establish the baseline.
- Show `FIRST RECORD` once on the exercise card in the active workout, history detail, post preview, and new feed snapshots. Use a neutral outlined label; keep fluorescent yellow filled badges for PRs.
- Before any valid completed set, show neither FIRST RECORD nor PR. All blocks with the same comparison key in the first session are first-record blocks; the session does not become its own prior history.
- FIRST RECORD contributes zero to prCount. Keep existing PostPRType's three values; add optional `recordStatus: 'first' | 'established'` on post exercise snapshots, and optional prVersion at post level.
- Preserve the existing live-screen FIRST RECORD hint for legacy workouts; the new classification is version 2 only.
- Mode changes never reset the baseline. First-ever VOLUME after a PR-only history is not FIRST RECORD; without an older valid VOLUME baseline it establishes volume history without VOLUME PR.

## Ordinary exercise rules

- WEIGHT PR: maximum weight among valid current sets exceeds the historical valid maximum; there must be a historical valid set.
- REP PR: a current set exceeds the maximum actual reps at exactly the same historical weight. A new weight has no REP PR baseline.
- VOLUME PR: positive volume exceeds older VOLUME-mode block volumes, with at least one valid older VOLUME block. PR focus never receives VOLUME PR.
- All numeric comparisons use stored kg values without rounding for display; validate input once and share its parsing across PR and text output. Define decimal input normalization explicitly, including comma input, without rewriting stored old strings.
- Every set compares to older sessions, not earlier sets in this session. Exercise badges combine distinct types; set badges prioritize WEIGHT PR before REP PR as today. prCount remains the number of badge types, not exercise count.

## PULL UP input and comparison

- Add optional `loadType: 'assisted' | 'bodyweight' | 'weighted'` to workout exercises, template exercises, and post exercise snapshots. Keep type='strength' and name='PULL UP'. Do not rename old exercises.
- Classification choice appears only for new PULL UP. Existing active legacy exercises remain unclassified unless the user explicitly chooses; retain their version 1 behavior. Do not edit saved history.
- Treat classification as exercise-level. If it changes after input, require the user to create another block rather than relabeling existing numeric inputs. Templates remember classification; old templates ask on new use.
- ASSISTED: label weight input `ASSISTANCE (kg)` and require a positive supplement value. BODYWEIGHT: reps input only, store explicit weight '0' for the established strength schema. WEIGHTED: `ADDED WEIGHT (kg)`, require positive added weight; zero belongs to BODYWEIGHT.
- BODYWEIGHT receives REP PR against prior classified BODYWEIGHT reps; no WEIGHT or VOLUME PR.
- WEIGHTED uses ordinary rules with added weight only. Volume is added weight x reps, clearly labeled as such, never bodyweight-inclusive load.
- ASSISTED and BODYWEIGHT have volume=0 and no VOLUME PR until effective load is defined. Display a dash/appropriate reps summary instead of presenting 0kg as measured training load. Their valid completed sets still contribute to totalSets; mixed totalVolume sums only defined volume. Explain that displayed volume excludes these classifications.
- Previous-set copy and LAST SESSION must match both name and classification. Never copy unknown PULL UP into a classified exercise. Keep legacy records visible as `PULL UP · LEGACY / UNCLASSIFIED` with the original values.
- Copy text: `PULL UP (ASSISTED)` + `40kg assistance x 8`; `PULL UP (BODYWEIGHT)` + `8 reps`; `PULL UP (WEIGHTED)` + `10kg added x 8`. Legacy copy stays unchanged.
- CHIN UP and DIPS retain existing behavior and are not classified in this release.

## Proposed ASSISTED WEIGHT PR — needs explicit approval

Use the lowest assistance at the **same actual rep count** as the comparison baseline. A valid current set qualifies only if a historical set at that rep count exists and assistance is strictly lower. REP PR remains higher reps at exactly the same assistance.

This conservative rule avoids extrapolating strength from assistance alone, avoids a formula/estimated 1RM, and ensures fewer reps cannot be called an assistance improvement against a higher-rep record. The badge can remain WEIGHT PR for compatibility, with a visible detail such as `LESS ASSISTANCE · 8 REPS`.

| Prior classified record | New set | Proposed outcome |
| --- | --- | --- |
| 40kg assistance x 8 | 30kg x 1 | No WEIGHT PR: no same-rep baseline |
| 40kg assistance x 8 | 30kg x 8 | WEIGHT PR |
| 40kg assistance x 8 | 40kg x 9 | REP PR |
| 40kg assistance x 8 | 30kg x 10 | No badge yet: both exact comparison baselines absent |
| 40kg assistance x 8 | 50kg x 8 | No PR |
| No classified history | 30kg x 8 | FIRST RECORD only |

Tradeoff: lower assistance plus more reps can be an obvious improvement but receives no badge without an exact baseline. An alternative is a historical non-dominated assistance/reps frontier, but that changes what WEIGHT PR means and adds state/comparison complexity. Prefer the conservative rule for v1.1 unless rewarding those mixed improvements is required. Equipment equivalence is not stored; comparisons assume the same assistance setup. Do not claim different machines or resistance bands are equivalent.

## Storage and old-client compatibility

- Never change old session IDs, names, strings, PR snapshots, timestamps, outbox entries, or local migration originals. No destructive bulk migration.
- Keep current JSONB columns, nonnegative aggregates, three PR strings, and RLS. Optional metadata needs validation and preservation in the adapters but should not require RLS changes.
- Old parsers accept optional unknown object fields, but old feed rendering cannot interpret a classified bestWeight. For classified snapshots, keep legacy display fields neutral (`bestWeight=0`, `bestReps=0`, `volume=0` for assisted/bodyweight), and store actual classified summary values in a validated optional `loadSummary` object. A short generated note conveys assistance/reps or added weight to old clients. Weighted snapshots may keep bestWeight as positive added weight and volume as added-weight volume, with the note stating its meaning.
- New readers use loadSummary; old readers retain a visible post instead of rejecting a new enum in prTypes. Do not rely on optional setResults: ordinary snapshots do not always contain all sets.
- Local history retains full sets; posting still uses a snapshot. Failed/pending snapshots retry unchanged even after upgrade. Already published posts are never recalculated or overwritten.

## Approval points

1. Accept neutral outlined FIRST RECORD, per name + classification, excluded from prCount?
2. Accept missing prVersion=1; version 2 from newly started workouts only; ordinary old sets remain baselines, unknown PULL UP does not?
3. Accept same-rep assistance WEIGHT PR and its conservative no-badge case for simultaneous assistance/reps changes?
4. Accept establishing an initial VOLUME baseline without VOLUME PR when earlier history is PR-only?
5. Accept block-level VOLUME comparison and added-weight-only WEIGHTED volume?
6. Accept volume=0 compatibility aggregates plus explicit exclusion labels, optional loadSummary, and old-client fallback notes?
