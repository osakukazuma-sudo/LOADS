### Database and deployment

Applied to `YOUR_PROJECT_REF` through the authenticated dashboard after explicit approval.

- `deleted_posts`: authenticated owner can read only their tombstones; clients cannot write/delete them.
- `delete_owned_post`: service_role-only RPC, SECURITY INVOKER, actor derived from validated Auth user in Edge Function. One transaction writes tombstone, durable photo cleanup job and deletes the post. Repeated deletion is idempotent.
- Post INSERT trigger takes a transaction advisory lock shared with deletion and refuses a deleted logical post ID. No direct client DELETE privilege is added.
- Restrictive Storage policies deny reinsertion and owner read of a deleted photo path.
- `photo_cleanup_jobs`: clients have no access. Jobs survive successful cleanup to catch uploads which began before deletion.
- `delete-post` deployed with platform JWT verification enabled and explicit Auth getUser verification.
- `deletion-worker` deployed using a dedicated database-generated credential; platform JWT verification is off because it receives this credential instead of a user JWT. Handler verifies it through a service-only RPC before work. The credential is never copied to application code or logs.
- Cron `loads-deletion-cleanup` runs every minute. Verified real HTTP 200 with `{processed:0,failed:0}` before deletion testing.
- Failed Storage removal remains due after 1 minute; successful removal is reconciled again after 24 hours. Cleanup uses the Storage API, never SQL DELETE on storage.objects.
- Dashboard deploys exact single-file bundles generated by `node scripts/prepare-edge-dashboard.cjs` from the local entry point and shared functions, with pinned supabase-js 2.117.1 and its official CORS header list. CLI deploy is available after CLI login; CLI is not currently authenticated.
